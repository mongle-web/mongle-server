# 마이페이지 닉네임 변경 (#101)

## API 계약

온보딩을 완료한 사용자가 본인의 닉네임만 변경한다. 최초 가입을 완료하는
`POST /api/v1/users/me/onboarding`과 분리하며 가입 크레딧을 지급하거나 사용하지 않는다.

```http
PATCH /api/v1/users/me/nickname
Authorization: Bearer {accessToken}
Content-Type: application/json

{"nickname":"새몽글"}
```

성공은 `200`과 `Cache-Control: no-store`이며 기존 `ApiResponse<UserResponse>`의 `data`에
`userId`, `email`, 변경 후 `nickname`, `onboardingCompleted=true`를 반환한다.
사용자 ID는 JWT에서 결정한다. 본문은 nickname만 허용하며 userId·email·onboardingCompleted 등 다른 필드는 거절한다.

## 검증과 저장

- 기존 온보딩과 같은 `NicknamePolicy`를 사용한다. 한글 완성형·자모·영문·숫자 2~10자다.
- null·빈 값·공백·특수문자·이모지는 허용하지 않는다. 앞뒤 공백도 제거하지 않고 잘못된 입력으로 처리한다.
- 닉네임 중복은 허용한다. '사용 가능한 닉네임' 문구는 입력 형식 검증 안내이며 별도 중복 확인 API는 없다.
- 같은 닉네임의 재요청은200이며 DB UPDATE와 updatedAt 변경 없이 현재 정보를 반환한다.
- 사용자 행 잠금 안에서 조회·검증·변경한다. 다른 사용자의 정보·가입 상태·이메일은 변경하지 않는다.
- 최초 온보딩은 기존 계약을 유지한다. 변경 API로 온보딩을 완료하거나 가입 혜택을 우회할 수 없다.
- 변경은 크레딧 기능 활성화·잔액·결제 보류와 무관하다. 기존 가입 지급·원장·잔액을 유지하고 소급 지급하지 않는다.
- 기존 Access/Refresh 세션을 유지한다. 변경 응답으로 프론트 회원 상태를 갱신하고 필요한 화면에서 GET /api/v1/users/me로 재조회한다. 닉네임 변경 때문에 별도 로그인·토큰 재발급을 요구하지 않는다.

## 오류

| HTTP | 코드 | 의미 |
| --- | --- | --- |
| 400 | COMMON_400_2 | nickname 누락·null·형식/길이 위반 |
| 400 | COMMON_400_1 | 잘못된 JSON·허용하지 않은 필드 |
| 401 | 기존 인증 코드 | 인증 누락·유효하지 않거나 만료/로그아웃된 세션 |
| 403 | USER_403_1 | 온보딩 미완료 |
| 404 | USER_404_1 | 내부 서비스 호출 시 사용자 없음 |

도메인 서비스에서 nickname 검증이 실패하면 기존 `USER_400_1`을 사용한다.
일반 HTTP 요청은 DTO 검증에서 먼저 거절하므로 `COMMON_400_2`로 반환한다.

## 적용·검증 범위

기존 users.nickname을 사용하므로 새 테이블·컬럼·마이그레이션은 추가하지 않는다.
H2·실제 HTTP 테스트로 변경 후 조회·기존 토큰 유지·본인 한정·잘못된 입력·무변경·중복 이름 허용·
크레딧 비활성 상태의 기존 회원 변경과 Swagger를 확인한다. 가입 혜택 테스트는 지급 이력이 있는 회원의 변경·온보딩 재요청 후에도
기존 지급·원장·잔액이 유지되는지 검증한다. 실제 운영 배포·MySQL·카카오 로그인 종단 검증은 별도다.
