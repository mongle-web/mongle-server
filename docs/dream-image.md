# 꿈 이미지 생성 및 결과 보존 기반

## 범위와 연결 상태

완료된 최신 장면 분석과 이야기로 이미지 생성을 예약하고 결과를 보존한다. 실제 이미지 모델 호출과 운영 저장소는 각각 `ImageGenerator`, `ImageAssetStore` 구현으로 연결해야 한다. 기본 Bean은 사용 불가 상태이고 생성 요청에 503을 반환한다. Mock 이미지를 운영 API에서 반환하지 않는다. Archive 목록, 캘린더, 결제·크레딧 차감, 공개 공유는 이번 범위에 포함되지 않는다.

10/8 확정 예정인 스타일·분위기 선택지는 코드에 임의로 정하지 않았다. `mongle.image.styles`, `mongle.image.moods` 허용 목록을 운영 설정으로 공급한다. 키는 `[a-z][a-z0-9-]{0,49}`이고 중복을 허용하지 않는다. 스타일 목록이 비어 있으면 생성 불가다. 스타일은 필수, 분위기는 선택이며 null은 별도 분위기 선택이 없음을 뜻한다. Provider 연결 전에 PM의 선택지 및 분위기 필수 여부를 확인해야 한다.

## API

모든 API는 인증이 필요하고 응답에 `Cache-Control: no-store`를 설정한다. 이미지 생성은 온보딩 완료 사용자만 가능하다.

| Method | Path (`/api/v1` 기준) | 결과 |
| --- | --- | --- |
| GET | `/image-options` | 설정된 styles/moods 키 |
| POST | `/dreams/{dreamId}/image` | 생성·재사용·재시도; PROCESSING 202, COMPLETED/FAILED 200 |
| GET | `/dreams/{dreamId}/image` | 살아 있는 원문에 연결된 최신 이미지 메타데이터 |
| GET | `/images/{imageId}` | 소유자의 보존 이미지 메타데이터; 원문 삭제 후에도 가능 |
| GET | `/images/{imageId}/download-url` | 소유자의 마지막 성공 파일용 5분 이내 HTTPS 임시 URL |

생성 본문: `revision`, `style`, 선택적 `mood`, 기본 false인 `regenerate`, 재생성 시 필수 `imageVersion`. `revision`은 꿈의 낙관적 잠금 버전이고 이미지의 `imageVersion`과 다르다. 최초 요청은 완료된 최신 분석과 COMPLETED 이야기가 필요하다. 다른 사용자의 꿈/이미지는 404로 처리한다.

분석당 하나의 현재 이미지 레코드를 사용한다. 같은 입력의 성공 결과는 재사용한다. 이야기 JSON 해시, 원문 입력 버전 `sourceRevision`, 옵션 중 하나가 달라지면 명시적 재생성이 필요하다. 재생성은 마지막 조회의 imageVersion을 보내야 한다. 실패 또는 임대 만료 시 상태를 조회한 후 다시 요청할 수 있다. 이전 성공 결과가 남아 있으면 일반 재시도는 마지막 시도의 스타일·분위기·원문 입력 버전·이야기 해시가 모두 같을 때만 허용한다. 입력이 달라졌거나 이전 성공 옵션으로 되돌리려면 `regenerate=true`와 최신 `imageVersion`을 전달해야 한다. 이전 성공 결과가 없는 최초 실패/만료는 허용된 옵션으로 일반 재시도할 수 있다. 활성 시도와 같은 입력의 중복 요청은 해당 PROCESSING 결과를 반환하고 Provider를 다시 호출하지 않는다. 입력이 다른 활성 요청에는 충돌을 반환한다.

생성기 계약은 `CompletableFuture<byte[]>`이며 HTTP 응답도 Spring MVC 비동기 처리로 완료한다.
새 생성 요청은 결과가 완료될 때 200, 같은 입력의 진행 중 요청은 바로 202를 반환한다.
응답을 기다리는 HTTP 연결은 남지만 요청 스레드나 대기용 풀 작업은 점유하지 않는다.
클라이언트의 연결 종료나 반환 Future 취소는 내부 업로드·DB 기록을 취소하지 않는다.
별도 영속 작업 큐는 없으며 서버 재시작 시 자동으로 이미지 모델을 재호출하지 않는다.

`MONGLE_IMAGE_MAX_CONCURRENT_CALLS`는 인스턴스별 진행 작업 한도이며 기본 2, 허용 범위는 1~16이다.
슬롯은 제공자 호출 전 확보하고 파일 검증·업로드·완료/실패 기록이 끝날 때 반환한다.
기존 성공 결과 및 같은 입력의 진행 결과를 재사용할 때는 슬롯을 요구하지 않는다.
새 작업의 한도 초과 또는 서버 종료 중에는 `503 / IMAGE_503_2`를 반환하고 예약 변경을 롤백한다.
Provider를 호출하거나 기존 성공 결과를 변경하지 않는다. 클라이언트는 잠시 후 명시적으로 재시도한다.
이 한도는 분석/서사화 풀과 별개이며 여러 인스턴스를 합친 한도나 서비스 토큰 과금을 보장하지 않는다.

제공자 완료 콜백에는 검증·JPA·스토리지를 실행하지 않는다. `image-result-*` 전용 풀은
최대 2개의 스레드(한도 1이면 1개), 큐 용량은 진행 작업 한도와 같다.
완료 작업은 슬롯당 하나만 제출한다. 파일 디코딩과 동기 스토리지 I/O가 실행되는 동안은
이 제한된 스레드를 사용하며, 외부 이미지 응답을 기다리는 데 사용하지 않는다.
스토리지 put/delete/URL 발급의 실제 어댑터는 타임아웃을 설정해야 한다.
다운로드 URL 발급은 기존 동기 API를 유지한다.

외부 호출은 DB 트랜잭션 밖에서 실행하고 예약·완료·실패만 짧은 별도 트랜잭션에서 처리한다.
사용자 행 잠금을 기존 분석·이야기·꿈 편집과 공유한다. 시도 임대는 2분이다.
Provider 어댑터는 비동기 HTTP를 사용하고 전체 호출 타임아웃을 이보다 짧게 설정해야 한다.
블로킹 SDK를 `supplyAsync`로 감싸거나 이 서비스에서 `join/get`으로 기다리는 구현은 금지한다.
만료된 시도는 다음 명시적 요청으로 재시작할 수 있고 늦게 도착한 결과는 현재 결과를 덮어쓰지 않는다.
앱 종료 시 신규 작업을 막고 최대 5초만 완료를 기다린다. 이후 미완료 상태는 lease와 다음 요청으로 처리하며
유료 호출 성공 여부가 불명확할 수 있으므로 자동 재호출하지 않는다.

현재 완료 분석을 원문 수정 후 다시 분석하는 API는 선행 구현에도 없다. 원문 수정 후 최신 분석·이야기가 없으면 새 이미지 생성을 막고 이전 성공 결과만 보존한다. 원문 재분석 흐름을 이번 이미지 기능에 포함한 것으로 취급하지 않는다.

## 보존·편집 정책

이미지는 원문이 아닌 보존 분석 `DreamAnalysis`에 연결한다. 원문 삭제 시 생성 중 이미지는 SOURCE_DELETED로 실패시키고 이미 저장한 성공 파일과 분석은 유지한다. `sourceDeleted=true`, `dreamId=null`이며 `/images/{imageId}`로 계속 조회한다. 생성 중 원문 내용이 바뀌면 SOURCE_CHANGED, 이야기 JSON이 바뀌거나 최신 이야기 생성이 진행 중이면 STORY_CHANGED로 실패하고 새 업로드를 폐기한다. 제목만 바뀌면 입력 내용 버전이 같으므로 저장을 허용한다. 원문 감정·분석·통계는 이미지 생성으로 수정하지 않는다.

재생성 중이거나 실패한 경우 마지막 성공 파일은 보존한다. `style/mood`는 현재 시도, `resultStyle/resultMood/resultRevision`은 화면에 표시할 성공 파일의 입력이다. `hasPreviousResult=true`이면 이전 성공 파일을 표시할 수 있다. `sourceChanged/storyChanged`는 표시 가능한 마지막 결과가 현재 입력과 다른지 알려준다. 상태 PROCESSING/FAILED 자체가 파일 없음이라는 뜻은 아니다.

## Provider·스토리지 계약

`ImageGenerator.generate`는 비동기 결과를 반환하며 콜백 스레드에서 파일 저장이나 JPA를 호출하지 않는다.
네트워크 어댑터는 응답 크기를 제한하고 원문·이미지 바이트·외부 오류 본문을 로그에 남기지 않는다.
`ImageGenerator.Input`은 사용자/이미지/시도 식별자, `image-v1-story`, 옵션, 검증된 이야기 sections를 제공한다. 원문·이야기 전문의 별도 DB 스냅샷은 추가하지 않는다. SCENE과 AI_BRIDGE를 구분하고 Provider 어댑터에서 실제 프롬프트를 작성한다. 입력/출력의 toString은 이야기와 바이트를 노출하지 않는다. 기존 LLM Gateway의 텍스트 출력 계약에 이미지 바이트를 억지로 추가하지 않는다.

서버가 파일 헤더와 실제 디코딩을 검증한다. PNG/JPEG, 최대 10 MiB, 각 변 최대 8192, 총 픽셀 최대 16,777,216만 허용한다. MIME·확장자는 응답 문자열을 신뢰하지 않는다. 저장 경로는 서버 생성 `dream-images/{userId}/{imageId}/{attemptId}.png|.jpg`다. 버킷/컨테이너는 비공개여야 하며 `put`은 콘텐츠 유형도 적용해야 한다. URL이나 스토리지 키는 메타데이터 API에 노출하지 않는다.

스토리지 `put`은 해당 파일을 조회할 수 있는 상태에서 성공을 반환하고, `delete`는 객체가 이미 없어도 성공하는 멱등 동작으로 구현한다. 어댑터에서 실패 원인에 키나 서명 URL을 담더라도 API 경계는 이를 공통 예외 로그로 넘기지 않는다. 내부 서비스는 최초 실패와 보상 실패의 관계를 보존한다.

`temporaryUrl`은 HTTPS와 5분 이하 유효기간을 보장해야 한다. 사용자정보가 있는 URL, 만료된 URL, 더 긴 URL은 거절한다. 서명 URL/키/외부 예외 메시지를 로그에 남기지 않는다. 업로드 및 DB 저장 실패, 입력 변경, 뒤늦은 결과는 **해당 시도의 새 객체만** 삭제한다. 정리 실패 시 경고를 남긴다. 성공 객체를 잘못 삭제하지 않도록 스토리지의 미참조 객체 회수는 DB storage_key 참조와 생성 중 시도를 확인해야 한다. 경로 전체에 무조건 TTL을 적용해서는 안 된다.

DB와 외부 저장소는 원자적이지 않다. 프로세스 중단과 보상 삭제 실패에 대비한 실제 미참조 객체 회수 작업은 운영 스토리지 연결 시 필요하다. 재생성 성공 후 이전 파일은 즉시 삭제하지 않는다. Archive·결제의 보존 정책 확정 후, 현재 참조와 감사/보존 정책을 반영한 정리를 구현한다. 이전 이미지들의 목록/이력 API가 구현된 것은 아니다.

## SQL 및 검증

신규 DB는 `db/schema-initial.sql`, 기존 MySQL 8 DB는 앞선 #19 SQL 적용 후 `db/migrations/20261006-dream-image.sql`을 수동 적용한다. `dream_images` 신규 테이블만 만든다. 기존에 같은 이름의 테이블이 있다면 실제 컬럼을 비교해야 하며 CREATE IF NOT EXISTS가 호환성을 검증하지는 않는다. 앱/AI 호출 중지 및 백업 상태에서 실행하고 Hibernate validate로 확인한다. 실행 스크립트는 운영 SQL을 자동 실행하지 않는다.

H2 MySQL 모드에서 전체 회귀 테스트와 초기 스키마 validate를 검증한다. 실제 MySQL 실행, 이미지 Provider 호출, 운영 스토리지 및 PM 옵션은 검증되지 않았다. 이 항목이 준비되기 전에는 이미지 기능이 운영 완료된 것으로 취급하지 않는다.

## #38 검증 범위

기존 이미지 보존·재생성·수정/삭제·SQL 테스트는 비동기 결과를 기다리도록 변경했다.
추가 테스트는 미완료 Future의 즉시 반환, 실행 한도와 재사용, 예약 롤백 시 슬롯 반납,
공개 Future 취소 후 내부 완료, 전용 완료 스레드, 실패 이후 슬롯 재사용 및 비동기 예외 비밀정보 제거를 확인한다.

작업 환경에서 Java 소스 233개의 구문 검사와 `git diff --check`를 통과했다.
Java 17 별도 실행 검증에서는 스레드 팩터리만 호환 코드로 바꿔 실행 한도·취소 후 완료·실패 복구·중복 반납을 50회 검증했다.
