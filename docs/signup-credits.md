# 가입 완료 3크레딧 지급 (#93)

## 지급 시점과 대상

카카오 로그인으로 계정을 처음 만들 때는 닉네임이 비어 있고, 이때는 지급하지 않는다. Bearer 인증으로 `POST /api/v1/users/me/onboarding`의 최초 닉네임 등록을 완료할 때 기본 3크레딧을 지급한다. 닉네임 등록·크레딧 계정·SIGNUP 지급·GRANT 원장은 동일 트랜잭션에서 저장한다. 지급 실패 시 닉네임 등록도 롤백한다.

- `CreditService.grant(userId, SIGNUP, "signup:" + userId, configuredAmount)`를 사용한다. 입력의 다른 계정 ID·지급량·요청 키를 받지 않는다.
- 사용자 행 잠금으로 동시 요청을 직렬화한다. 같은 닉네임의 반복/동시 완료 요청은 추가 지급하지 않는다. 다른 닉네임으로 완료 계정을 덮어쓰는 요청은 기존409로 거절한다.
- 기존 가입 완료 계정에는 조회·재로그인·닉네임 재요청으로 소급 지급하지 않는다. 기존 테스트 계정은 운영자용 PROMOTION 도구로 필요한 양을 별도 지급한다.
- 이 배포 전에 카카오 로그인만 하고 닉네임을 아직 등록하지 않은 계정은 배포 후 최초 온보딩을 완료할 때 지급 대상이다.
- 이미 가입을 완료하고 지급받은 뒤 설정 수량이 바뀌어도 재요청으로 추가 지급하거나 기존 수량을 바꾸지 않는다.
- 가입 혜택은 몽글 크레딧이다. OpenAI 계정의 API 잔액 지급·페이앱 결제·결제 상품 승인과 별개다.

## 설정과 실패

| 환경변수 | 동작 |
| --- | --- |
| `MONGLE_CREDIT_ENABLED` | 기존 기본 false. 신규 가입을 완료하려면 true여야 함 |
| `MONGLE_CREDIT_EXPIRY_POLICY` | 기존 기본/허용 정책 NO_EXPIRY |
| `MONGLE_CREDIT_SIGNUP_AMOUNT` | 기본3. 운영 확정값3을 명시하거나 기본값 사용 |

미설정/빈 값의 바인딩 기본값은3이다. 음수는 기존 설정 검증에서 거절하고, 명시적0 또는 내부 null 정책으로 신규 지급을 시도하면 `CREDIT_503_1`로 거절한다. 크레딧 기능이 꺼졌을 때도 신규 온보딩은 HTTP503/CREDIT_503_1이고 닉네임·지급·원장을 남기지 않는다. 혜택 없이 가입만 완료되는 상태를 만들지 않는다.

기존 온보딩 완료 계정의 동일 닉네임 재요청은 새 지급이 아니므로 크레딧 비활성 상태에서도 기존 성공을 반환한다. 일반 로그인·내 정보 조회·기존 크레딧 조회에 별도 제한을 추가하지 않는다.

## 배포 전 인프라 확인

신규 가입 혜택을 제공하는 릴리스이므로 PR 머지·CD 전에 인프라 담당자가 아래 **비밀이 아닌 설정값**을 확인한다. `/etc/mongle/mongle.env`의 키/비밀번호/파일 전체는 채팅이나 로그에 공유하지 않는다.

```dotenv
MONGLE_CREDIT_ENABLED=true
MONGLE_CREDIT_EXPIRY_POLICY=NO_EXPIRY
MONGLE_CREDIT_SIGNUP_AMOUNT=3
```

과거 `MONGLE_CREDIT_SIGNUP_AMOUNT=0`을 명시했다면3으로 수정한다. 환경 파일을 바꾼 경우 기존 운영 절차로 mongle 서비스를 재시작하고 health를 확인한다. 파일 수정만으로 이미 실행 중인 JVM의 값이 바뀌지는 않는다. PayApp 판매 기능을 켤 필요는 없으며 기존 결제 플래그·JWT·OAuth·DB·S3 설정은 보존한다.

DB 구조·새 Flyway 버전·마이그레이션 권한은 필요 없다. `SIGNUP` 출처와 지급/원장 테이블은 이미 존재한다. 운영 DML 계정을 유지하며 기존 계정 일괄 지급 SQL은 실행하지 않는다. #92 지급 도구와 함께 사용할 때에도 이 가입 로직이 운영 명령을 호출하지는 않는다.

## 프론트 연결

기존 닉네임 완료 API의 요청/응답 DTO는 바뀌지 않는다. 가입 완료 성공 후 기존 API로 새 잔액을 읽는다.

1. 실제 카카오 로그인 → CSRF/Refresh → `onboardingCompleted=false` 확인.
2. `POST /api/v1/users/me/onboarding`에 `{"nickname":"몽글러"}` 전송.
3. 성공 응답으로 회원 상태를 갱신한다. 온보딩 전 Access Token도 계속 사용할 수 있다.
4. `GET /api/v1/credits/balance`의 `available=3`, `reserved=0`, `total=3` 확인.
5. `GET /api/v1/credits/transactions`에 `kind=GRANT`, `source=SIGNUP`, `availableDelta=3` 내역 확인. 내부 지급 키는 공개 API에 나오지 않는다.

프론트에서 보유 크레딧을 임의로3 더하지 않는다. 재로그인/화면 재진입/새로고침 시 서버 잔액을 그대로 사용한다. 신규 온보딩이503으로 실패하면 가입 성공 화면으로 넘어가지 않고 재시도 안내한다. 이미 완료한 계정에서 다른 닉네임을 보내는 요청은409다.

## 검증 범위

공통 서비스 테스트를 H2와 실제 MySQL8.4의 DML/TLS 환경에서 실행한다. 기본3·설정 수량·카카오 재로그인·기존 계정 무소급·동일/다른 닉네임의 동시 요청·잘못된 닉네임·미존재 계정·기능 비활성·원장 실패·상위 트랜잭션 롤백을 검증한다. 가입 지급분으로 실제 원장의 예약3→실패 해제3→재예약/성공 확정0 흐름과 SIGNUP 출처 배분도 확인한다.

기존 실제 HTTP 인증 테스트는 온보딩 완료 뒤 동일 Access Token으로 잔액3·SIGNUP 내역을 조회하며 반복 요청이 추가 지급하지 않는지 확인한다. 테스트의 카카오 식별자는 모의 데이터이며, 운영 카카오 가입·실제 이미지 호출은 배포 후 별도 검증한다. 회원탈퇴/재가입 혜택 기준과 닉네임 편집은 이번 작업에 포함하지 않는다.
