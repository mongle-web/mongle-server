# 유료 크레딧 환불 접수 (#132)

## 프론트 연동

모든 경로는 온보딩을 완료한 회원의 Bearer 인증과 기존 `ApiResponse`를 사용한다. 응답에는 `Cache-Control: no-store`를 설정한다. 최신 약관 동의가 필요한 기존 회원도 환불 경로를 이용할 수 있다.

| API | 사용 |
| --- | --- |
| `GET /api/v1/payments/refunds/estimate?orderId={UUID}&reason=STANDARD` | 본인 주문의 구매·사용·예약·미사용 수량과 예상 원화 금액 확인 |
| `POST /api/v1/payments/refunds` | 해당 주문의 남은 유료분에 대한 접수 및 보류 |
| `GET /api/v1/payments/refunds/{receiptId}` | 접수 당시 산정 근거와 현재 산정 상태 확인 |
| `GET /api/v1/payments/refunds?beforeId=&size=20` | 내 접수 목록. 크기 1~50, `hasNext`이면 `nextBeforeId`를 다음 요청에 사용 |

요청 예시

```json
{
  "requestId": "6bf6a5ea-22a6-43ea-88dd-28780b42a3a1",
  "orderId": "5f5654b2-716c-4a25-944a-ae512ccf434b",
  "reason": "STANDARD"
}
```

`orderId`는 결제 API의 공개 주문 UUID다. `requestId`는 버튼을 누를 때 생성하고 같은 요청 재전송에 재사용한다.
일반 환불은 `STANDARD`, 청약철회·서비스 하자 등 판단이 필요한 신청은 `RIGHTS_REVIEW`를 사용한다.
금액·수량·결제사 번호는 클라이언트가 제출하지 않는다. 주문마다 접수 하나가 생성되며 동일 요청은 같은 `receiptId`로 응답한다.

접수 후 `receiptId`, `receivedAt`, `supportEmail`을 사용자에게 보여주고 저장할 수 있게 한다.
`initialStatus`와 `*AtRequest` 필드는 접수 당시 기록이다. `currentEstimate`는 예약 확정·해제나 결제 상태가 바뀐 뒤 다시 계산한 값이며, 접수 당시 시각을 기준으로 수수료 경계를 판정한다. 표시 문구는 ‘환불 신청 접수’로 하고, 예상액이 있는 경우에도 완료 또는 확정 금액으로 표시하지 않는다.

| 산정 상태 | 화면 처리 |
| --- | --- |
| `ESTIMATED` | 예상 금액과 공제율 표시 |
| `WAITING_RESERVATION` | 진행 중인 이미지 사용량을 확인한 뒤 예상액 갱신. 접수는 가능 |
| `REVIEW_REQUIRED` | 승인 시각 미확인, 별도 권리 검토 또는 기존 결제 취소 확인. 금액은 null |
| `NO_REFUNDABLE_BALANCE` | 일반 환불에 사용할 미사용분 없음. 권리 검토 접수는 별도 안내 |

| 오류 | 처리 |
| --- | --- |
| `REFUND_404_1` | 없는 주문·접수 또는 타인 소유 |
| `REFUND_409_1` | 이미 접수된 주문 또는 요청 UUID 충돌. 접수 목록 확인 |
| `REFUND_409_2` | 주문·지급 내역이 신청 조건을 충족하지 않음 |
| `REFUND_503_1` | 접수 기능 준비 전 |
| 400 | 요청 형식·페이지 값 확인 |

크레딧 잔액 API는 원장 합계를 반환한다. 환불 접수된 구매분의 미사용량은 위 접수 응답에서 확인한다.
보류분은 새 이미지 예약에서 빠지므로 원장 잔액만 충분하고 실제 차감 가능한 금액이 부족하면 `CREDIT_409_1`을 반환한다.
기존의 결제 취소 확인 보류는 `CREDIT_409_5`로 처리된다.

## 산정과 탈퇴

- 일반 예상액은 원주문 결제액 × (미사용 수량 ÷ 구매 수량)이다. 검증한 승인 시각부터 정확히 168시간까지 공제율은 0%, 그 이후 일반 환불 공제율은 10%다. 공제를 포함한 전체 산식의 결과를 마지막에 한 번 원 단위로 올림한다.
- [페이앱 결제통보 문서](https://docs.payapp.kr/dev_center01.html)의 `pay_date`를 KST 기준으로 해석해 신규 지급의 최초 승인 시각에 저장한다. 지원 형식은 `yyyyMMddHHmmss`, `yyyy-MM-dd HH:mm:ss`다. 주문 생성 이전, 통보 시각 이후, 누락·파싱 실패와 기존 주문의 승인 시각은 검토 대상으로 남긴다. `responsedate`는 기존 통보 인증·유효성 확인에 사용한다.
- 실제 지급과 동일한 사용자 행 잠금에서 주문·구매 지급분·예약·소유자를 다시 확인한다. 환불 신청은 기존 결제 취소 보류와 별개이며, 해당 구매분의 차감만 막는다. 기존 이미지 예약의 성공·실패 처리는 계속 가능하다.
- 모든 남은 유료 구매분이 접수 범위에 포함되면 탈퇴를 진행한다. 기존 탈퇴 처리에서 진행 중 예약을 해제하므로 접수된 유료분은 그 범위 내에서 다시 미사용분으로 돌아간다. 접수 이후 추가로 지급된 다른 구매분이 있으면 그 구매분도 확인한다.
- 탈퇴 후 로그인 세션은 해제된다. 사용자는 탈퇴 전에 저장한 접수번호로 고객센터에 문의한다. 접수번호는 검색 식별자이므로 고객센터는 거래와 신청자 확인을 거쳐 상태를 안내한다.
- 미완료 환불은 거래 보존기간이 지났어도 파기하지 않는다. 페이앱에서 이미 취소된 주문을 회수하는 기존 명령도 접수된 건을 거절하므로 동일 구매분을 이중 처리하지 않는다.

## 배포와 공개

1. 기존 CD로 `V9__payment_refund_intake.sql`을 적용한다. 기존 결제의 승인 시각과 환불 접수 건은 백필하지 않는다.
2. `MONGLE_PAYMENT_REFUND_ENABLED` 기본값은 false다. 활성화 시 공개 문의 주소 `MONGLE_PAYMENT_REFUND_SUPPORT_EMAIL`이 필요하다.
3. 실제 페이앱 취소와 크레딧 회수, 접수 종료·보류 해제 처리 경로를 준비한 뒤 공개한다. 이 배포의 상태는 접수 및 검토 대기다.
4. 신규 접수를 끌 때도 이미 접수된 건의 조회·보류·탈퇴 확인·보존은 계속 동작한다. 문의 주소는 유지한다. 접수가 생성된 운영 DB에서 V9 이전 앱은 새 구매분 보류를 읽을 수 없으므로 신규 접수를 중지할 때는 V9 앱의 설정을 사용한다.

운영자는 접수번호로 `payment_refund_requests`와 원주문·지급 원장을 대조한다.
서버의 예상액은 실제 카드 취소 증빙을 대신하지 않으므로 페이앱 거래 확인 후 후속 정산 경로에서 처리한다.
