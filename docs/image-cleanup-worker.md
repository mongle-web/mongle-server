# 이미지 정리 요청 워커 (#50)

## 범위와 기본 동작

#49의 `image_cleanup_requests`를 처리한다. 꿈 삭제의 DB 원자성과 삭제된 결과의 404 계약은 유지한다.
#54의 S3 어댑터를 포함한 `ImageAssetStore.delete`를 호출한다. 워커는 기본 비활성이다.
활성화해도 스토리지가 unavailable이면 요청·시도 횟수를 보존한다. 신규 이미지 생성이나 AI/크레딧 호출은 없다.
#71의 세계관 이미지 폴더 삭제·교체/실패·만료 정리도 처리하며 현재 성공/유효 시도는 보호한다. 꿈 삭제 후 보존하는 세계관 이미지와 과거 모든 파일 스캔은 정리하지 않는다.

## 상태와 등록

| 상태 | 의미 | 다음 동작 |
| --- | --- | --- |
| PENDING | 정리 요청 대기 | next_run_at 이후 예약 |
| PROCESSING | claim token과 유효한 lease로 소유한 작업 | 외부 삭제 후 결과 저장 |
| RETRY_WAIT | 삭제 실패/참조 보호/일시 사용 불가 | next_run_at 이후 재확인 |
| COMPLETED | 객체 삭제 성공 또는 이미 없음 | 새로운 정리 요청이 없으면 재실행하지 않음 |
| HELD | 최대 시도 소진 | 자동 실행 중지, 원인 확인 후 내부 등록 계약으로 재요청 |

`failure_code`는 STORAGE_DELETE_FAILED, RETRY_EXHAUSTED, STORAGE_UNAVAILABLE, REFERENCED, ACTIVE_ATTEMPT 등 고정 내부 코드만 사용한다.
보류를 성공으로 표시하지 않는다. 공개 상태/관리자 API는 이번에 추가하지 않았다.

꿈 삭제와 보상 삭제 실패는 사용자 행 잠금 → 정리 요청 잠금 순서로 같은 등록 서비스를 사용한다.
키가 같은 PENDING/RETRY_WAIT 요청의 재전송은 기존 백오프·시도 횟수를 초기화하지 않는다.
COMPLETED/HELD에 새 정리 요청이 들어오면 같은 행을 PENDING으로 재등록한다.
PROCESSING에 도착한 요청은 requeue_requested로 합친다. 현재 삭제가 성공해도 즉시 완료로 끝내지 않고 한 번 더 처리한다.
외부 삭제 IO가 끝난 직후 새 업로드가 생겼을 가능성을 포함하기 위한 계약이다.
현재 삭제가 실패하면 기존 실패 재시도/상한 정책으로 새 요청도 함께 처리한다. 상한 소진 시 HELD에 보존한다.

최초 요청의 소유자·이미지 ID·사유·dreamId는 유지한다. 재등록을 새 원본 본문/분석 복제 수단으로 사용하지 않는다.
행과 키의 삭제 시작 표시는 보존한다. 완료 행을 임의로 지우는 보관기간 정책은 후속 설계다.

## 예약·보호·외부 IO

1. 짧은 읽기 트랜잭션에서 커밋된 대기/만료 ID를 제한 개수로 조회한다.
2. 사용자 → 정리 요청 순서로 잠그고 실행 자격/현재 파일 참조/활성 생성 시도를 재검사한다.
3. 예약은 시도 횟수를 늘리고 새 claim token·lease·삭제 시작 표시를 같은 트랜잭션에서 저장한다.
4. 별도 제한된 실행기에서 IO 직전 토큰·lease·파일 참조를 다시 확인하고, 트랜잭션 종료 뒤 delete를 호출한다.
5. 짧은 결과 저장 트랜잭션에서 토큰과 유효 lease를 확인하고 완료/재시도를 확정한다.

마지막 성공 storageKey는 이미지 상태가 FAILED/PROCESSING이어도 보호한다. 활성 시도의 `.png`/`.jpg` 키도 보호한다.
예약 전 참조 보호는 삭제 시도 횟수를 늘리지 않고 RETRY_WAIT로 미룬다. 예약 후 IO 직전 재검사에서 보호된 건은 이미 부여한 시도 횟수를 유지한다. 기존 이미지/꿈 삭제로 참조가 사라지면 다시 처리한다.
제어 스레드는 외부 IO를 기다리지 않는다. 실행 중/대기 합계는 인스턴스별 max-concurrent-calls 이하이고 큐도 유한하다.
예약/IO 직전 검사는 READ_COMMITTED를 사용한다. 소유자 조회 후 사용자 잠금을 기다렸더라도 그 사이 공개된 파일 참조를 다시 읽어야 하기 때문이다. [MySQL 격리 수준 문서](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html)를 기준으로 선택했으며 실제 MySQL 검증은 별도다.
여러 인스턴스의 같은 요청 예약은 DB 사용자/요청 잠금과 토큰으로 직렬화한다. 동시 실행 설정은 인스턴스별 상한이다.

외부 IO 중에는 행 잠금을 유지하지 않으므로 토큰만으로 파일 삭제 자체를 취소할 수는 없다.
따라서 최초 삭제 시작 시 deletion_started_at을 영속 기록하고, 이미지 완료 저장은 이 표시가 있는 키의 채택을 ASSET_DISCARDED로 거절한다.
이 표시는 재등록/만료/완료에도 해제하지 않는다. 시도별 키는 재사용하지 않는 기존 `dream-images/{userId}/{imageId}/{attemptId}.{ext}` 계약을 유지해야 한다.
정리 요청이 대기/참조 보호 중이며 삭제 시작 전이라면 정상 활성 이미지 완료는 가능하다.
같은 성공의 완료 재전송은 이미 참조된 동일 파일을 보상 삭제 대상으로 돌리지 않는다.
현재 파일 참조를 우회해서 쓰는 새 저장 경로는 이 사용자 잠금·삭제 시작 검사를 함께 적용해야 한다.

## 실패와 복구

삭제 실패는 retry-base-delay부터 지수 백오프하고 retry-max-delay에서 제한한다.
외부 호출 직전 스토리지가 unavailable이거나 실행 제출에 실패하면 시도 횟수를 돌려놓고 재확인한다.
삭제 성공 뒤 DB 기록 실패/프로세스 중단은 PROCESSING 상태를 남긴다. lease 만료 후 새 토큰으로 멱등 삭제한다.
객체가 이미 없어도 저장소 delete는 성공해야 한다. 만료/교체된 토큰의 늦은 완료는 상태를 덮어쓰지 않는다.
최대 시도에 도달한 실패/만료는 HELD에 남긴다. 계속되는 실패에서 무한 재시도/중복 차감을 만들지 않는다.

스토리지 어댑터는 요청 시간 제한을 lease보다 짧게 두고 종료 시 인터럽트/취소 계약을 지켜야 한다.
lease가 외부 요청을 강제로 취소하지는 않는다. 느린 이전 삭제와 복구 삭제가 겹칠 수 있으므로 같은 키 삭제가 멱등이어야 한다.
종료는 신규 예약을 막고 최대 5초 기다린 뒤 실행기 종료를 요청한다. 남은 PROCESSING은 다음 기동에서 lease로 복구한다.
외부 키/서명 URL/오류 본문은 로그에 출력하지 않는다. 완료 저장 장애는 고정 경고를 남긴다.

## 설정

| 환경변수 | 기본값 | 의미 |
| --- | --- | --- |
| MONGLE_IMAGE_CLEANUP_ENABLED | false | 실제 워커 활성화 |
| MONGLE_IMAGE_CLEANUP_POLL_INTERVAL | 2s | 예약 조회 주기 |
| MONGLE_IMAGE_CLEANUP_BATCH_SIZE | 20 | 한 번에 살펴볼 후보 상한 |
| MONGLE_IMAGE_CLEANUP_MAX_CONCURRENT_CALLS | 2 | 인스턴스별 실행 상한 |
| MONGLE_IMAGE_CLEANUP_LEASE | 2m | 예약 유효기간 |
| MONGLE_IMAGE_CLEANUP_RETRY_BASE_DELAY | 30s | 첫 재시도/참조 재확인 간격 |
| MONGLE_IMAGE_CLEANUP_RETRY_MAX_DELAY | 1h | 백오프 상한 |
| MONGLE_IMAGE_CLEANUP_MAX_ATTEMPTS | 5 | 실패/만료 포함 최대 삭제 시도 |

설정값의 범위를 기동 시 검사한다. 실제 저장소 연결/시간 제한/권한 확인 후 명시적으로 활성화한다.
실제 S3 요청·운영 파일 삭제를 이번 작업에서 실행하지 않았다.

## SQL과 검증

새 DB는 갱신된 schema-initial.sql을 사용한다.
기존 DB는 #49의 20261014-image-cleanup-requests.sql 이후 20261018-image-cleanup-worker.sql을 수동 적용한다.
앱/이미지 워커 중지 및 백업 후 적용하고 Hibernate validate로 확인한다. DDL은 자동 커밋되며 운영 적용하지 않았다.
컬럼/인덱스 존재 검사로 재실행할 수 있다. 기존 요청은 PENDING·시도 0·next_run_at=created_at으로 전환한다.
재실행으로 PROCESSING/COMPLETED 등 기존 상태를 초기화하지 않는다. 이미 잘못 정의된 컬럼/인덱스의 자동 교정은 하지 않는다.

가짜 저장소/H2로 삭제 후 처리·다른 객체 보존·없는 객체·실패 백오프·상한·중복 예약·만료/늦은 완료·재등록·참조 보호·제한된 실행·롤백·완료 DB 저장 실패 복구를 검증한다.
초기 SQL/JPA validate와 MySQL 마이그레이션의 컬럼/백필/인덱스 정의 재실행을 H2에서 확인한다.
실제 MySQL 8 프로시저 원문 실행·S3·다중 서버 운영 부하 검증과 구분한다.

PR base는 미병합 #49의 feat/48-dream-delete-derived-data다. #52에서 #39와 통합했으며 비동기 완료에도 삭제 시작 검사·등록 재요청 계약을 유지한다. [통합 계약](image-async-integration.md)을 참고한다.

## S3 어댑터 (#54)

비공개 S3 put/delete/서명 URL 구현과 기본 비활성 설정은 [S3 연동 계약](image-s3.md)을 따른다.
SDK 요청 재시도와 이 워커의 영속 시도 횟수는 구분한다. 호출 제한은 worker lease보다 짧아야 한다.
참조 보호/삭제 시작 검사/재등록 계약은 유지한다. 실제 운영 S3 삭제와 버전 관리 버킷의 과거 버전 회수는 검증하지 않았다.
