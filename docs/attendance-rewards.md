# 일일 출석 보상 (#121)

## 지급 정책

Bearer 인증과 닉네임 온보딩을 완료한 회원이 출석 보상 버튼을 누르면 한국 시간 기준 하루 한 번 기본 1크레딧을 받는다. 로그인·조회만으로는 지급하지 않는다. 가입 당일에도 SIGNUP 3크레딧과 별개로 받을 수 있고, 지급분은 기존 NO_EXPIRY 정책을 따른다.

하루는 `Asia/Seoul`의 00:00부터 다음 날 00:00 직전까지다. 마지막 수령 이후 24시간이 아니라 다음 한국 시간 자정에 새 보상이 열린다. 빠진 날짜의 소급 지급·연속 출석 보너스·월간 달력은 제공하지 않는다. 기존 가입 완료 계정도 오늘 보상을 받을 수 있다.

## API

두 API 모두 요청 본문 없이 본인 계정으로 호출하며 사용자 ID·날짜·지급량·내부 지급 키를 입력받지 않는다. 기존 ApiResponse 래퍼와 `Cache-Control: no-store`를 사용한다.

### GET /api/v1/attendance

오늘의 상태를 조회한다. 지급 기록·크레딧 계정·잔액을 만들거나 변경하지 않는다. 기능이 꺼져 있어도 조회할 수 있다.

응답의 `data` 예시:

```json
{
  "date": "2026-11-02",
  "claimed": false,
  "rewardAmount": 1,
  "claimable": true,
  "nextClaimAt": "2026-11-02T15:00:00Z"
}
```

- `date`: 서버가 계산한 한국 기준 오늘 날짜.
- `claimed`: 오늘 보상 지급 이력 유무. 지급분을 모두 사용해도 true다.
- `rewardAmount`: 미수령이면 현재 설정량, 수령했다면 해당 날짜의 실제 지급량.
- `claimable`: 오늘 미수령이고 전체 크레딧·출석 기능이 모두 활성화됐는지 표시한다. 조회 뒤 다른 탭에서 수령하거나 운영 설정이 바뀔 수 있으므로 최종 결과는 POST 응답으로 확인한다. 잔액 범위 초과 같은 최종 지급 실패까지 미리 보장하지 않는다.
- `nextClaimAt`: **다음 날짜** 보상이 열리는 한국 시간 자정의 UTC Instant다. 아직 오늘 보상을 받지 않았다면 이 시각까지 기다릴 필요가 없다.

### POST /api/v1/attendance/claim

오늘 보상을 수령한다. 신규 수령·이미 수령한 재요청 모두 HTTP 200이다.

응답의 `data` 예시:

```json
{
  "date": "2026-11-02",
  "amount": 1,
  "alreadyClaimed": false,
  "balance": {
    "available": 4,
    "reserved": 0,
    "total": 4,
    "spendingBlocked": false
  },
  "nextClaimAt": "2026-11-02T15:00:00Z"
}
```

재요청은 `alreadyClaimed=true`이고 `amount`는 기존에 지급한 수량이다. 추가로 지급했다는 뜻이 아니다. `balance`는 응답 처리 시점의 현재 잔액으로, 최초 수령 이후 이미지 사용·결제 등으로 달라질 수 있다.

보상량이 변경되거나 기능이 꺼져도 이미 지급한 당일 보상은 기존 지급량으로 재확인한다. 기능 비활성 상태의 신규 지급만 503으로 거절한다. 다음 날짜의 요청은 해당 날짜 보상을 대상으로 하므로 전날 응답을 그대로 돌려주지 않는다.

## 저장과 동시성

`AttendanceService`가 `CreditService.grant`를 호출하고 출처 `ATTENDANCE`, 키 `attendance:{userId}:{yyyy-MM-dd}`를 사용한다. 별도 출석 테이블이나 지급 스케줄러 없이 기존 `credit_grants`를 출석 지급 기록으로 사용한다. 출석 기능을 껐다 켜거나 보상량을 변경해도 같은 날짜의 키를 변경하지 않는다.

사용자 행을 가장 먼저 잠근 뒤 날짜를 한 번 결정하고 해당 요청 전체에 사용한다. 잠금 대기 중 자정을 넘었다면 잠금 획득 후 날짜를 사용한다. 지급량·잔액·지급 기록·GRANT 원장은 하나의 트랜잭션으로 저장하며 실패하면 모두 롤백한다. 동일 사용자에 대한 결제·이미지 예약/확정/해제와 같은 잠금 순서를 따른다. 출처·키 해시의 기존 고유 제약도 중복을 방어한다.

지급 이력은 `GET /api/v1/credits/transactions`에서 `kind=GRANT`, `source=ATTENDANCE`로 반환한다. 원장·API의 기록 시각은 기존 UTC 정책을 유지하고 출석 날짜 계산에만 한국 시간대를 사용한다. 내부 지급 키와 해시는 응답에 포함하지 않는다.

출석 지급은 기존 결제 사용 보류를 해제하지 않는다. 보류 계정도 보상 수령은 가능하지만 `balance.spendingBlocked=true`와 이미지 사용 제한은 유지한다. 기존 크레딧 배분·예약·실패 해제·성공 확정에 그대로 사용할 수 있다.

## 오류와 설정

| 상황 | HTTP / 코드 |
| --- | --- |
| 미인증·유효하지 않은 토큰 | 기존 인증 오류 401 |
| 온보딩 미완료 | 403 / USER_403_1 |
| 사용자 없음 | 404 / CREDIT_404_1 (HTTP 인증 단계에서 먼저 거절될 수 있음) |
| 내부 지급 키 불일치 | 409 / CREDIT_409_2 |
| 잔액 long 범위 초과 | 409 / CREDIT_409_4 |
| 전체 크레딧 또는 출석 기능 비활성의 신규 지급 | 503 / CREDIT_503_1 |

| 환경변수 | 기본값 / 동작 |
| --- | --- |
| MONGLE_CREDIT_ENABLED | false. 신규 출석 지급에도 true 필요 |
| MONGLE_CREDIT_EXPIRY_POLICY | NO_EXPIRY |
| MONGLE_CREDIT_ATTENDANCE_ENABLED | false. 출석 보상만 독립적으로 개방 |
| MONGLE_CREDIT_ATTENDANCE_AMOUNT | 1. 양의 정수만 허용하며 0·음수는 시작 시 거절 |

출석 보상을 개방할 설정 예시:

```dotenv
MONGLE_CREDIT_ENABLED=true
MONGLE_CREDIT_EXPIRY_POLICY=NO_EXPIRY
MONGLE_CREDIT_ATTENDANCE_ENABLED=true
MONGLE_CREDIT_ATTENDANCE_AMOUNT=1
```

기존 가입·결제·이미지 설정은 유지한다. 설정 변경은 프로세스에 반영해야 한다. 새로운 enum 값을 이전 버전의 서버가 읽지 않도록 **모든 서버·워커를 새 버전으로 교체한 뒤** 출석 지급을 활성화한다. 이후 ATTENDANCE 지급이 생겼다면 해당 출처를 모르는 구버전으로 롤백하지 않는다.

새 테이블·컬럼·Flyway 버전은 필요 없다. 적용된 V1·기존 수동 초기 스키마를 수정하지 않는다. 운영 DB나 운영 환경변수는 이 구현 작업에서 변경하지 않는다.

## 프론트 연결

1. 화면 진입 또는 앱 복귀 시 GET으로 오늘 상태를 조회한다.
2. `claimed=true`면 '수령 완료', 미수령·`claimable=true`면 '보상 받기', 비활성이면 이용 불가 상태를 표시한다.
3. 클릭 시 POST를 호출하고 요청 중 중복 클릭을 막는다. 서버도 중복 요청을 한 번만 지급한다.
4. 성공 시 수령 완료로 표시하고 **응답의 balance로 교체**한다. 로컬 잔액에 amount를 더하지 않는다.
5. 이미 수령한 응답은 추가 지급 축하/증가 애니메이션을 반복하지 않는다. 이용 내역의 ATTENDANCE는 '출석 보상'으로 표시한다.
6. 요청 실패·응답 유실은 재조회 또는 POST 재시도로 복구한다. 503이면 성공 화면으로 바꾸지 않는다.
7. nextClaimAt 이후 또는 화면 재진입 시 상태를 다시 조회한다. 기기 날짜나 타이머만으로 미수령 상태를 확정하지 않는다.

프론트 코드 변경은 별도 저장소에서 진행한다. 새 source 값에 대한 타입·표시 대응을 함께 배포한다.

## 검증과 운영 점검

H2 통합 테스트와 이를 상속한 `AttendanceMysql84Test`가 첫 수령·동시 수령·반복 요청·한국 자정/월말/연말·잠금 대기 중 날짜 변경·가입 당일 수령·설정 변경·비활성·인증·온보딩·전체 롤백을 검증한다. 기존 이미지 예약과의 경합 및 출석 지급분의 예약→해제→성공 확정, 결제 보류 보존도 확인한다. Swagger에서 두 응답과 ATTENDANCE 출처를 검증한다.

실제 MySQL 8.4 테스트는 기존 `python3 scripts/mysql84-test.py`의 일회용 TLS/DML 전용 DB에서 실행한다. 운영 DB를 테스트 대상으로 사용하지 않는다.

출시 후 일별 수령 회원 수·ATTENDANCE 지급량·이미지 성공 및 무료 재생성 건수·실제 Provider 비용을 함께 확인한다. 수령률의 분모는 같은 한국 날짜의 온보딩 완료 방문 회원 수로 정의한다. 현재 방문 집계가 없으면 수령 건수와 지급량부터 보고 수령률을 추정하지 않는다. 보상량 1 기준 30일 수령은 30크레딧이며 실제 비용은 이미지 사용과 무료 재생성에 따라 달라진다. 지급량은 사용자에게 미리 안내하고 설정으로 조정한다.
