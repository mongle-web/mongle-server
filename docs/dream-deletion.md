# 꿈 영구 삭제와 이미지 파일 정리 요청 (#48)

## API 계약

`DELETE /api/v1/dreams/{dreamId}?revision={revision}`은 최신 revision과 소유권을 확인한다.
타인/없는 꿈은 동일한 404, 오래된 revision은 409다. #46의 생성 보호 검사와 사용자 행 잠금을 유지한다.
분석·서사 명시적 재생성 대기/진행과 활성 이미지·브리지 작업은 삭제를 차단한다.
최초 자동 생성의 기존 입력 변경 계약과 lease 만료 후 변경 허용 계약은 유지한다.

성공 응답은 개별 DB 데이터 삭제와 파일 정리 대상 기록이 커밋됐다는 뜻이다.
실제 저장소 파일 삭제가 끝났다는 뜻은 아니다. 원문/결과를 응답·삭제 이력에 복제하지 않는다.

## 같은 트랜잭션에서 제거하는 데이터

1. 해당 꿈을 앞/뒤로 참조하는 브리지 결과. 다른 연결은 유지하고 새 이웃 연결은 생성하지 않는다.
2. 확인 가능한 마지막 성공 이미지의 비공개 파일 정리 요청 기록. 저장 실패 시 1번도 롤백한다.
3. 모든 서사 성공 버전 → 현재 서사 → 개별 이미지 메타데이터.
4. 장면-요소 연결 → 장면 → 요소 → 표시 키워드 → 분석.
5. 자동 생성 예약/진행 작업 → 감정 → 꿈.

현재 원문 ID와 소유자를 기준으로 범위를 제한한다. 분석에 연결된 데이터와 분석 없이 꿈에 직접 연결된 기존 장면/요소도 포함한다.
FK 삭제 순서를 지키고 벌크 제거 뒤 영속성 컨텍스트를 비운다. 다른 꿈·사용자 그래프와 AI 사용량/비용 감사 로그는 유지한다.
분석·서사·성공 버전·이미지 단건/URL 재발급 및 꿈/Archive 조회는 404다.
늦은 완료·실패 콜백은 기존 행만 갱신하므로 삭제 행을 재생성하지 않는다. 이미 진행하던 생성 요청도 삭제된 결과라면 404로 끝난다.

## 이미지 파일 정리 경계

`image_cleanup_requests`에는 `user_id`, nullable `dream_id`, `image_id`, `storage_key`, `reason`, `created_at`만 저장한다.
원본 삭제 뒤에도 처리해야 하므로 삭제 대상 부모와의 FK는 없다. 키는 유일하며 공개 DTO/Swagger/일반 로그로 내보내지 않는다.
행의 처리 상태/시도/lease는 [정리 워커 계약](image-cleanup-worker.md)을 따른다. 워커는 기본 비활성이며 실제 S3 어댑터는 별도다.

- `DREAM_DELETED`: 이미지 상태가 성공/실패/만료여도 남아 있는 마지막 성공 storageKey를 삭제 트랜잭션 안에서 기록한다.
  성공 파일이 없는 실패/진행 행은 정리 요청 없이 제거한다. 정리 요청 저장이 실패하면 삭제도 취소한다.
- `DISCARDED_UPLOAD`: 만료·입력 변경·삭제·저장 실패로 채택되지 않은 시도의 새 업로드를 기존 방식으로 보상 삭제한다.
  보상 삭제도 실패하면 별도 짧은 트랜잭션으로 해당 키를 기록한다. 같은 사용자 잠금과 키 유일 제약으로 재전송을 중복 기록하지 않는다.
  삭제 후 늦은 업로드에는 원본 ID를 알 수 없으므로 dream_id가 null일 수 있다. 원본/분석/이미지 행은 복원하지 않는다.

외부 저장소 IO는 삭제 트랜잭션에서 수행하지 않는다. 정리 워커는 커밋된 요청만 소비하고,
현재 성공 참조/유효한 생성 시도가 없는 것을 확인한 뒤 멱등 `delete`를 실행해야 한다.
실패 재시도·중단 복구·중복 실행·완료 표시는 #50에서 구현했다. 실제 어댑터/비밀 키 관리·보관 기간은 저장소 연결 시 설계한다.
세계관 전체 이미지 키는 이 테이블에 넣지 않는다.

현재 이미지 행에는 마지막 성공 키 하나만 있다. 이전 재생성의 모든 파일 키를 회수했다고 주장할 수 없다.
업로드 직후 프로세스 중단, 보상 삭제와 정리 요청 DB 기록이 모두 실패한 경우는 영속 요청만으로 복구할 수 없다.
키/외부 오류 메시지 없는 경고와 운영 저장소-DB 대조 회수가 필요하다. 경로 전체 TTL로 성공 참조까지 지우지 않는다.
이미 발급한 서명 URL은 최대 5분 만료 전까지 유효할 수 있다. 즉시 URL 폐기는 이번 범위가 아니다.

## 통계와 과거 데이터

월간 분석 건수·키워드·최근 분석 대상에 현재 dream FK 존재 조건을 추가했다.
기존 성공 판정/날짜 범위/상한은 유지하고 감정 통계는 현존 꿈 감정만 집계한다.
이전 배포에서 dream FK가 해제된 보존 분석도 제외한다. 같은 날짜에 다시 기록한 새 꿈과 섞지 않는다.

기존 FK 분리 분석과 파일을 자동 일괄 삭제하는 작업은 없다. 기존 데이터 호환을 위해 nullable FK와 sourceDeleted 응답 필드는 남긴다.
운영 정리 전에는 dream FK 부재·sourceDreamId의 원본 존재/소유권·서사/이미지/향후 세계관 참조를 조회해 대상을 확인하고,
백업·파일 목록 대조·작은 단위의 수동 정리 계획을 별도로 마련한다. 감사 로그를 꿈 내용처럼 일괄 제거하지 않는다.

## SQL과 의존 PR

기존 MySQL에는 `src/main/resources/db/migrations/20261014-image-cleanup-requests.sql`을 수동 적용한 후 배포한다.
새 DB는 갱신된 schema-initial.sql을 사용한다. 기존 DB에 전체 초기 SQL을 재적용하지 않는다.
마이그레이션은 CREATE TABLE IF NOT EXISTS로 재실행 가능하지만 이미 존재하는 잘못된 스키마를 자동 교정하지 않는다.
운영 DB는 실행하지 않았다. H2 MySQL 모드 초기 SQL/JPA validate 및 마이그레이션 재실행 검증과 실제 MySQL 검증을 구분한다.

브랜치와 PR base는 `feat/46-dream-generation-guards`(#47)다. develop에 선행 PR이 합쳐졌다고 가정하지 않는다.
#39 비동기 이미지 PR과 통합할 때 cleanup(input, key, failure)의 영속 정리 전달·NOT_FOUND 전파·생성 보호를 유지해야 한다.

## 세계관 후속 계약

현재 세계관 폴더/선택 목록/완성 작품 참조 테이블은 없다. 테이블을 추가할 때 해당 꿈을 사용한 선택 목록과 완성 작품을 모두 찾고,
삭제 트랜잭션에서 서사/브리지 참조를 먼저 제거한 뒤 현재 삭제를 호출해야 한다. 참조가 남으면 FK 오류로 전체 롤백되어야 한다.
B 삭제 시 B와 AB/BC만 제거하고 AC는 자동 생성하지 않는다. 폴더·남은 구성·기존 전체 이미지는 0~1개에서도 유지한다.
새 세계관/전체 이미지 재생성의 최소 꿈 수 2개 정책은 후속 API에서 적용한다.
영향 세계관 조회/부분 제거가 없는 현재 API를 전체 세계관 삭제 정책 완료로 안내하지 않는다.
